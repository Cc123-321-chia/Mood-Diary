# Security Design Guide

## Best security story for Vivian's Diary Management module

### 1. Authentication first

**Design:** All diary operations require the team login session through `requireUser()`.

**Reason:** The browser must not be allowed to choose `user_id`. If the frontend sends a user ID, an attacker could change it.

**Implementation:** `save_diary.php`, `delete_diary.php`, `upload_media.php` call `requireUser()` and obtain the user ID from the server session.

### 2. Object-level authorization / IDOR prevention

**Design:** A diary ID is not sufficient authorization.

For Edit/Delete/Upload, the backend checks that the requested diary belongs to the authenticated user:

`WHERE diary_id = ? AND user_id = ?`

**Threat prevented:** User A changes `diaryId=5` to `diaryId=6` and edits/deletes User B's private diary.

This should be one of the strongest security points in the report.

### 3. SQL Injection prevention

**Design:** Use PDO prepared statements for all values.

**Threat prevented:** Malicious diary content or IDs changing the SQL query.

Diary text is stored as data, never concatenated into SQL.

### 4. CSRF protection

**Design:** A random token is stored in the authenticated session. `get_diaries.php` sends it to the dashboard; mutation requests send it back in `X-CSRF-Token`.

**Protected actions:** Create, Edit, Delete, Upload and Profile Update.

This works together with the team's `SameSite=Strict` and `HttpOnly` session cookie for defense in depth.

### 5. Secure file upload

Do not trust the HTML `accept` attribute because attackers can bypass frontend validation.

Server controls used:

- MIME allowlist using `finfo`
- JPEG/PNG/WebP/GIF + MP4/WebM only
- image/video size limits
- max 9 media per diary
- random filenames generated with `random_bytes()`
- upload path is generated by server; user cannot choose it
- `.htaccess` blocks script execution in upload directory
- ownership check before attaching media to a diary

**Threats reduced:** malicious executable upload, path manipulation, overwriting files, oversized uploads.

### 6. XSS prevention

Diary content is rendered through `escapeHtml()` rather than inserted as trusted HTML. Media URLs are restricted by `safeUrl()`.

**Threat prevented:** diary content such as `<script>...</script>` becoming executable browser code.

### 7. Error handling

Detailed PHP/SQL exceptions go to `error_log()`. Users receive generic messages such as `Could not save diary`.

**Reason:** Database names, SQL structure and server paths should not be exposed to users.

### 8. Security logging

Create, Update, Delete and Media Upload try to add an event to `security_logs` with user ID, event type, IP and user agent.

**Use in report:** accountability, incident investigation and audit trail.

# Project-level security issues to raise with the team

## HIGH — Admin authorization is not complete

The v2 admin APIs currently start a session but do not demonstrate an admin-role check. A normal logged-in user must never be able to call User Management APIs simply by knowing the URL.

**Recommended design:** separate `requireAdmin()` guard using an authenticated admin identity/role, applied to every admin page/API before data access.

## HIGH — SMTP secret was stored in source code

An App Password appeared in `config/mail_config.php` and screenshots. It should be considered exposed.

**Action:** revoke it, generate a new one, and store the replacement only in `mail_config.local.php` or environment variables. Never commit it.

## MEDIUM — Admin module has missing/inconsistent files

The v2 ZIP references JavaScript/API files that are not included. Fix these before security testing so missing client code is not mistaken for an authorization failure.

## MEDIUM — Profile avatar validation

`update_profile.php` still stores avatar data supplied by the browser. For a stronger final design, validate image MIME/size server-side or move avatar upload to a dedicated secure upload endpoint.

## MEDIUM — Email enumeration

`forgot_password.php` correctly returns a generic response. However `check_email.php` explicitly returns whether an email is registered. Decide whether that endpoint is truly required; otherwise remove/restrict/rate-limit it.

## Design/report rule

Only claim controls that are actually implemented. For example, the schema may contain a `sessions` table, but the current login implementation primarily uses PHP sessions. Do not claim database-backed session management unless the code actually uses that table.
